## What Vastos is

A Next.js 16 (App Router, TypeScript) SaaS app: upload a floor-plan image → AI extracts rooms → user confirms/edits rooms → picks a design style → AI generates photorealistic interior renders per room → user edits/approves → a walkthrough video + PDF export is produced. India-focused (Indian design styles, room types like Pooja Room, Rupee-oriented). Zustand local-first store (`src/lib/store.ts`, persisted to localStorage) with a best-effort Supabase mirror. Supabase also provides admin-issued-only auth (no public signup).

Read `CLAUDE.md` and `AGENTS.md` in this checkout for the full architecture writeup — both are kept up to date and are more authoritative than this document for anything about *how the code currently works*. This document is about *what happened across sessions* and *what's still open*.

**No test runner exists in this repo.** The actual verification suite, every time, is:
```bash
npx tsc --noEmit
npm run lint
npm run build
```
`npm run build` matters specifically because it catches client/server-boundary bugs (`"use client"` components transitively importing server-only code) that `tsc` alone misses.

### 21. Delete-project menu genuinely not working — root-caused as a real onBlur/click race, not a stacking bug this time (2026-07-30, same day, COMPLETE pending live confirmation)

Fixed at the source: new `src/lib/ist-date.ts` — `istDateInputToIso(dateStr)` parses a date-input string with an explicit `+05:30` offset instead of letting it default to UTC; `isoToISTDateInput(iso)` is the inverse, for correctly redisplaying a stored value back into the date input (this direction had the identical bug un-reported: slicing a UTC ISO string's first 10 characters can show the wrong calendar day to an IST admin near the day boundary). Applied to BOTH `console/user-row.tsx` date inputs — Scheduled stop (what was reported) and Billing anchor date (identical bug shape, not yet reported but fixed proactively since it's the same input pattern). Verified the conversion directly (`2026-07-31` → `2026-07-30T18:30:00.000Z`, i.e. genuine IST midnight, round-trips back to `2026-07-31`) before considering this done, per the debugging skill's "test the fix, don't just believe it" step. `tsc`/lint/build all clean.

**Not fixed**: the "boss" account's already-stored bad value (`2026-07-31T00:00:00Z`, 5.5h later than the admin likely intended) was left as-is rather than silently rewritten — it's self-correcting (will still take effect, just ~5.5h later than intended) and editing live production data without being asked felt like overreach. ## Conventions worth knowing before touching code here

- Follow `superpowers:brainstorming` → `writing-plans` → `subagent-driven-development` for anything non-trivial and big enough to warrant it; for a batch of independently-scoped tasks, direct parallel `Agent` dispatch (implementer + independent `tsc`/lint verification per task) has repeatedly been the lighter-weight equivalent, used successfully across workstreams 5, 8, 9, and 11.
- No em dashes in UI copy (repo-wide rule, enforced during every review pass).
- Motion must be `transform`/`opacity` only, never `top`/`left`/`width`/`height`/`margin` (enforced repeatedly — caught real bugs in workstream 3's `GeneratingLoader` and used correctly in workstream 8's `RoomReorderModal`).
- Model selection for subagent dispatch: cheap/fast model for mechanical, fully-specified tasks — `sonnet` for anything requiring integration judgment across files — most capable model for a final whole-branch review. Always specify a model explicitly; an omitted model silently inherits the session's most expensive one.
- **If an `Agent` dispatch fails on a session/usage-limit error, don't just blindly retry** — check whether the agent had actually finished its file edits before hitting the limit (`tsc`/`git status`/reading the target files directly). Workstream 9 had 3 agents fail this way; one had fully completed its work already (verified, no rework needed), two hadn't started editing (redone directly). Retrying wastes an attempt if the work is already done, and silently re-running a partially-done task risks double-applying an edit.
- **`/code-review` (and its `ultra` variant) cannot be invoked by the model at all** — confirmed via a direct attempt (`disable-model-invocation`). If asked to "do a code review" and the user isn't available to trigger it themselves, do a manual multi-agent correctness/security review instead (as in workstream 11) and say so plainly rather than silently substituting without mentioning it.
- **When an API route accepts a client-resolved storage key** (an `imageKey`, `floorPlanImageKey`, or similar) in its request body, always validate both that the caller owns the project it's claimed to belong to AND that the specific key is actually part of that project's own data — never trust a key string outright just because the caller is authenticated. `src/lib/projects/approved-rooms.ts`'s `allowedProjectStorageKeys` is the established pattern for this (workstream 11, Finding 1); the public `/api/s/[token]/asset` route's `allowedAssetKeys` (workstream 8) is the same idea for the unauthenticated case.
- **When wrapping a third-party API client with this codebase's retry policy** (`ai/errors.ts`'s `RETRYABLE_CATEGORIES`), make sure the client actually throws typed `ProviderError`s with the right category, not plain `Error`s that get blanket-coerced to a retryable category by the wrapper. A client that never throws `ValidationError` for its own deterministic 4xx failures means every one of those failures gets retried at real cost (workstream 11, Finding 2) — this is easy to miss since the wrapper's `if (e instanceof ProviderError) throw e` silently does nothing when the inner client never actually throws one.
