# Plan: Vastos Revamp — Foundation + Thin-Slice MVP

## Context
Vastos is being repositioned from its current form (floor-plan upload → manual 3D furniture placement) into a B2B SaaS tool that lets construction/interior-design firms generate photorealistic AI room visuals and walkthrough videos to close clients. The user inherited the codebase and is revamping it end-to-end: real auth, a new flow, a new dark premium UI, a separate admin console, and a config-driven AI prompt system, while keeping the parts of the existing app that already work.

## Locked decisions
- **Codebase**: extend the existing app, do not rewrite from scratch.
- **Database**: stay on Supabase.
- **AI providers**: Google-only. Drop fal.ai/FLUX entirely. All generation (OCR, semantic reasoning, room images, inpainting edits, video) runs through Gemini/Imagen/Veo. Remove `FAL_*` env vars and `src/lib/render/flux-client.ts` usage.
- **Detection**: build both Gemini-vision-only room extraction and the existing OpenCV path behind a config toggle; decide which is live in production later, keep the other hibernating.
- **Hosting**: deferred until the detection toggle decision is made (Gemini-only unlocks plain Vercel; keeping OpenCV live needs a containerized host). Not a blocker for the thin-slice build.
- **Spend control**: no hard enforcement yet, log every AI call (user, model, feature, cost, duration) for the admin console to display.
- **Aesthetic presets (locked)**: Modern Minimalist, Contemporary Indian, Traditional/Ethnic Indian, Industrial/Urban Loft, Scandinavian-Warm, Luxury Classical.
- **Build order**: thin vertical slice first (new flow end-to-end with basic auth), harden/expand after.
- **Project Snapshot / Version History (locked, add now)**: every generation (room image, edit, video) is saved as a new snapshot, never overwrites a previous one. Users can browse and return to any prior generation of a project, the way design software keeps version history. See the new `generations` table and updated flow steps below.
- **Export Feature (locked, add now)**: a professional PDF export for completed projects — cover page, client name, project details, selected room renders, selected aesthetic, colour palette, and a walkthrough video link (not a QR code) — built for a builder to hand directly to their client.
- **Universal JSON Architecture (locked, final foundation)**:
  ```
  Frontend Input → Universal Input JSON → Planning Layer → Design Specification JSON → Prompt Builder → Gemini → Generated Images/Videos
  ```
  This is now the fixed backbone of the whole system, not open for future re-architecture. Hard rules: the frontend never constructs prompts, the frontend never knows prompt templates exist, and only structured JSON travels through the application until the Prompt Builder (provider layer only) converts it into the final natural-language prompt. Fully detailed in "AI prompting architecture" below.

## CTO review — architecture decisions incorporated
A CTO-level review of this plan raised several architecture questions. Decisions below; rationale inline where opinion was requested. Sections further down (Database, Admin console, Flow, Workstreams, Deferred) are updated to match.

- **Project state machine (add now)**: each project gets one backend-owned `status` field driving the whole lifecycle — `created → floor_plan_uploaded → parsing → needs_review → ready_for_generation → generating_images → images_ready → editing → generating_walkthrough → completed`, plus `failed`. The frontend renders off this single field instead of ad-hoc booleans (`isUploaded`, `isParsing`, etc.). This directly explains the crash reproduced earlier too — undefined-shaped data reaching the UI mid-transition is exactly what a single source of truth prevents.
- **Image generation stays synchronous for MVP** (Gemini latency is acceptable for single room images), but goes through the same provider-abstraction call shape (`src/lib/ai/provider.ts`) that video generation uses, so swapping it to an Inngest background job later is a call-site change, not a rewrite. Video generation stays async via Inngest as already planned.
- **"Luxury Level" replaces any budget concept**: Standard / Premium / Ultra Luxury, selected alongside aesthetic style and color, is a field in the Universal Input Schema (see "AI prompting architecture" section) rather than a key in a combinatorial template lookup.
- **Config-driven project types: yes, include now.** `/config/project-types/{residential,apartment,commercial,custom}.json`, each defining supported room types, walkthrough order, and the category's planner persona (see "AI prompting architecture"). Recommended because it's exactly what lets Custom verticals (dental clinic, pub, etc.) be added by writing a config file instead of new code paths, which the user explicitly wants.
- **Project Manifest: yes, but kept lightweight.** One structured JSON per project (metadata, Universal Input, detected rooms + edits, Design Specification, generation settings) — implemented as a single JSONB column on the existing `projects` row, not a new subsystem. It's the natural place the state machine, Design Specification, and room list already need to live together; building it as a separate service would be over-engineering for this size of product.
- **Design consistency across rooms: yes, include in MVP — see "AI prompting architecture" section below for the full design (superseded from an earlier "House Design DNA" framing into a project-type-agnostic Design Planning Layer).**
- **AI moderation / prompt safety** — explicitly Phase 2, not MVP. Future work: validate/sanitize prompts before they reach Gemini.
- **Image caching / generation reuse** — explicitly Phase 2, not MVP. Future idea: if an identical (project, room, style, luxury level, prompt version) combination was already generated, reuse it instead of a new AI call. Pure cost optimization, no MVP dependency on it.
- **Prompt management in the admin console: yes, add.** Prompt templates must be editable/versionable without a deployment — see Admin console section below.
- **General review call**: the Approvals tab in the admin console reference screenshot assumes self-serve signup; this product has admin-issued credentials only, so a real approval workflow has no purpose yet. Keep the tab visually present (matches the reference layout) but leave its logic as a Phase 2 stub — building real approval logic now would be speculative complexity with no current trigger for it.

## CTO review, round 2 — architecture decisions incorporated
- **Generation pipeline versioning: yes, include.** Every generation (image or video) records `pipeline_version`, `system_prompt_version`, `planning_prompt_version`, `prompt_builder_version`, `design_spec_version`, `model_used`, `post_processing_version` alongside the existing `ai_usage_logs` fields (updated from an earlier flatter version-field set to match the System/Planning/Builder template split — see "AI prompting architecture"). Cheap (a handful of extra columns), and it's what makes a bad output traceable to a specific template/spec/model combination later, and what image caching (Phase 2) will key off.
- **AI provider abstraction stays explicit and is now a hard rule**: only `src/lib/ai/provider.ts` is allowed to import a Gemini/Google SDK or call its REST endpoints directly. Every other module (pipeline stages, API routes, frontend) calls the provider layer's functions (`generateImage`, `editImage`, `generateVideo`, `runOCR`, `runSemantic`) and never a provider client directly. This was already the plan; stating it as an enforced rule rather than an implied pattern.
- **Feature flags: yes, include a lightweight version.** A single `feature_flags` table (key, enabled boolean, updated_at) plus a thin `isFeatureEnabled(key)` server-side helper. Justification: the plan already has several toggles that want exactly this (`DETECTION_MODE`, whether Inngest/async is on, which Luxury Levels are live, which project-type configs are enabled) — a tiny generic mechanism replaces one-off env vars for anything that should be toggleable without a redeploy, at near-zero added complexity. Explicitly NOT building: percentage rollouts, user targeting, or an admin UI for flags in this phase — flip flags via a direct DB update or a basic list in the console later if needed.
- **Retry policy for AI/storage operations**, applied inside the provider layer and storage helpers:
  - *AI provider timeout*: retry twice with exponential backoff. Timeouts are usually transient network/latency issues and cheap to retry.
  - *Temporary provider failure (5xx / rate limit)*: retry twice with backoff, capped low because each retry is a paid call — don't let a persistent outage silently rack up cost. Surface a failure to the user after retries are exhausted rather than retrying indefinitely.
  - *Storage upload failure*: retry up to 3 times, no AI cost involved so retrying is cheap and typically resolves transient network blips.
  - *Invalid user request (validation failure)*: never retry. It's a deterministic failure — retrying the same bad input just fails again. Surface immediately.
  - *Safety/content policy rejection*: never auto-retry with the same prompt (it will be rejected again). Surface a clear message asking the user to adjust their input; no silent retry loop.
- **Standardized error categories: yes, include.** `ValidationError`, `AiProviderError`, `StorageError`, `TimeoutError`, `InternalError` — used consistently in provider-layer responses, `ai_usage_logs`, and API error payloads. The frontend uses the category to decide whether to show a "try again" action (AiProviderError/TimeoutError/StorageError) or just a message (ValidationError/InternalError).
- **Manual room editing**: the current plan's room confirmation step already covers rename/retype. Adding the missing pieces the CTO review called out: delete room, add room (manual entry), and merge/split at the room-*list* level (combine two list entries into one, or duplicate one entry into two with user-assigned names). Precise geometry redraw (accurately re-slicing the visual floor-plan boundary when merging/splitting) is deferred to Phase 2 — for MVP, the room list drives prompt generation and the 2D plan display is illustrative, so list-level edits are sufficient without a geometry-editing engine.
- **Prompt architecture: superseded — see the dedicated "AI prompting architecture" section below**, which replaces the combinatorial `vertical:roomType:style:luxuryLevel` template-key model with a Universal Input Schema + Design Planning Layer + Prompt Builder pipeline.

## AI prompting architecture (revised)
Core philosophy: the frontend never thinks in prompts, it only collects structured data. The backend converts that structured data into AI decisions. AI stages talk to each other in structured JSON. Only the final step turns structured data into natural-language text, and only inside the provider layer.

**Pipeline stages, in order:**
1. **Structured input collection (frontend)** — the user answers screens (room list, style, luxury level, colour palette, one free-text "Additional Requirements" field). No prompt text is ever constructed or seen client-side.
2. **Universal Input Schema (backend, one shape for every project type)**:
   ```json
   {
     "project": { "category": "Residential", "subcategory": "Independent House" },
     "layout": {
       "rooms": [
         { "name": "Living Room", "size": "18 x 16 ft", "additional_notes": "Need lots of natural light." },
         { "name": "Master Bedroom", "size": "14 x 12 ft", "additional_notes": "Include a reading nook." }
       ]
     },
     "design": { "style": "Modern Minimalist", "luxury_level": "Premium", "colour_palette": "Warm White" }
   }
   ```
   Same shape for Residential, Apartment, Commercial, and Custom — only `project.category`/`project.subcategory` and the room list change. Internally, room width/height stay numeric (existing `Room.width`/`Room.height`); `size` is formatted as a string only at this schema boundary. **Per-room vs. global fields**: name, size, and additional requirements are edited per room, on the room confirmation screen — every room can ask for something different. Style, luxury level, and colour palette are the only global fields, chosen once and applied to every room, because visual consistency across rooms depends on them being shared (this is also what the Design Specification/Design Planning Layer needs held constant across rooms).
3. **Design Planning Layer (backend, one Gemini call per project, cached on `projects.manifest`)** — receives the Universal Input, returns one **Design Specification JSON**, never prose: Design Language, Material Palette, Lighting Strategy, Colour Strategy, Furniture Language, Camera Guidelines, Negative Constraints, and a **Room Guidelines** map (one entry per detected room, so the whole project's per-room guidance comes back in this single call rather than one call per room). The schema of this output is identical across project categories; what changes is the *planner persona* injected into the planning prompt from the project-type config (e.g. residential → "think like an interior designer creating a family home", restaurant → "think like a hospitality designer optimising ambience and customer experience", clinic → "think like a healthcare architect prioritising circulation, hygiene and comfort"). Runs once per project and is reused for every room and every "generate more" — not regenerated per room or per variation.
4. **Prompt Builder (provider layer only, deterministic, no AI call)** — assembles the final natural-language image-generation prompt for one room by combining: System Rules + Project Context (from the Universal Input) + Design Specification + this room's slice of Room Guidelines + Camera Rules + Negative Rules. This is the only place natural-language prompt text is produced.
5. **Image/video generation (provider layer)** — the assembled prompt goes to Gemini/Imagen/Veo via `src/lib/ai/provider.ts`.

**Versioning** (three independently versioned template types, all admin-editable via the Prompt Management console tab, published-flag gated so drafts don't affect live generation):
- **System prompt** — the fixed scaffolding/rules layer.
- **Design Planning prompt** — one per project category (holds that category's planner persona), produces the Design Specification.
- **Prompt Builder template** — the assembly logic/structure that turns System + Context + Design Spec + Room Guidelines into final text.

**What this replaces from earlier drafts of this plan:** the `vertical:roomType:style:luxuryLevel`-keyed `prompt_templates` rows (combinatorial, doesn't scale to new subcategories) and the residential-specific "House Design DNA" framing (now the project-type-agnostic Design Specification produced by the Design Planning Layer, which works identically for Residential, Restaurant, Clinic, Office, or any Custom category).

**Additional Requirements field**: replaces the earlier idea of separate boolean flags (pet-friendly, child-friendly, elderly-friendly, etc.) with one free-text field per room (not global), placeholder examples shown in the UI ("I want large windows", "Include a pooja room", "Seating for around 80 people"). It flows into `layout.rooms[].additional_notes` in the Universal Input, which the Design Planning Layer reads when producing that room's slice of Room Guidelines, and which the Prompt Builder includes in that room's assembled prompt.

**Explicitly not built now**: prompt caching beyond the one-planning-call-per-project reuse described above (broader generation caching stays Phase 2, per the earlier CTO review), and any UI that lets end users see or edit raw prompts — prompting stays entirely a backend/admin concern.

## Room structural context (doors/windows per room)
Gap identified: the pipeline already detects doors and windows as discrete points with orientation (OpenCV geometry, reconciled in `merge.ts` against a parallel Gemini-vision read), but never assigns them to a specific room or side — so a generated room image currently has no signal about where its real openings are.

- **Extraction — already covered, no new detection work.** Both active detection paths (OpenCV when live, Gemini vision when it's the active `DETECTION_MODE`) already produce door/window candidates in the same coordinate space as room boxes, reconciled by the existing merge logic.
- **Association (which room, which side) — new, and deliberately deterministic, not an AI call.** Once room boxes and opening points share plan coordinates (already true post-merge), assigning each opening to its nearest room edge is plain geometry: point-to-rectangle-edge distance, within a wall-thickness tolerance. A door can resolve to one room (an entrance) or two (connecting rooms); a window resolves to one room plus "exterior." This is reliable and free precisely because it's code, not model reasoning — Gemini is good at reading a plan's text and general layout, not at exact spatial math, so this step deliberately stays outside any AI call.
- **Reliability**: best-effort, bounded by upstream detection quality. A room with no detected openings gets an empty `openings` array — the prompt phrasing must never assert a room has no windows/doors, only state what was positively found, so a detection miss doesn't get compounded into a false hard constraint.
- **Explicitly excluded** (low reliability or low value from a 2D plan, not worth the complexity for a single-room render): full room-to-room wall-adjacency graphs, wall structural/load data, ceiling height.
- **Representation**: each room in `projects.manifest`'s room list gains a small `openings` array — `[{ "type": "door" | "window", "side": "north" | "south" | "east" | "west", "connectsTo": "Kitchen" | "exterior" | null }]`. No raw pixel coordinates leak into the AI-facing JSON; those stay internal to the geometry pipeline.
- **Pipeline stage**: a new deterministic step (e.g. `src/lib/pipeline/assign-openings.ts`) runs right after the Merge Engine, before the room list reaches the confirmation screen or gets written to the manifest — no added AI cost or latency of consequence.
- **Prompt integration**: each room's `openings` feeds the Design Planning Layer's per-room Room Guidelines (or is appended directly at the Prompt Builder step, whichever keeps the Design Planning call's output cleaner) and is translated to natural language only at the Prompt Builder step — e.g. "respect a window on the north wall and a door to the hallway on the south wall; do not invent additional openings." Never surfaced as raw JSON to the AI provider before that final assembly step, consistent with the rest of the prompting architecture.

## No-floor-plan flow: Sketch Tool (Phase 2, well-specified now; MVP stays the Q&A form)
Revises the earlier vague "floor-plan drawing tool" placeholder into a concrete, deliberately minimal design — not a CAD tool.

**Rejected approach**: freehand outer-boundary drawing + manual subdivision into room polygons. This is the genuinely hard part of any floor-plan software (polygon boolean operations, wall snapping, region-validity checking) and is disproportionate engineering for data that only needs to become the same structured JSON the upload path already produces.

**Why the existing lasso tool doesn't transfer here**: the app already has a freehand lasso for room creation (`lasso-select.tsx` + `lasso-extract.ts`), but its entire value comes from snapping the drawn loop to *real detected wall lines* and pulling *printed OCR dimension text* out of an already-uploaded, already-analyzed plan image. On a blank canvas there's no wall geometry to snap to and no text to extract — reusing it as-is would just be plain freehand-polygon-to-bounding-box drawing, i.e. exactly the rejected approach above, minus the snapping that makes it good in its actual context (the upload flow's "add a room" action, where it's reused unchanged — see "What's kept").

**Chosen approach — grid-block placement, not freehand drawing:**
- Rooms are placed as resizable rectangles snapped to a coarse grid (drag to place, drag an edge/corner to resize) — closer to arranging blocks than drawing lines. No separate "draw the boundary" step: the building footprint is simply the union of placed blocks.
- Two room-blocks placed edge-to-edge *is* the adjacency signal, so wall-sharing is known by construction, never inferred.
- Per room: type (dropdown), dimensions/area (auto-computed from grid cells × unit, user-editable override), unit toggle (ft/m) — same fields as originally proposed.
- Openings: click-to-cycle on a room's edge (none → door → window → none). If that edge borders a neighboring block, a door there resolves to `connectsTo` = that room; if it's on the outer boundary, it resolves to `connectsTo: "exterior"`. No geometric inference required, unlike the upload path's `assign-openings.ts`.

**Output**: identical `Room` + `openings` shape used everywhere else in the pipeline (see "Room structural context" above), feeding the same manifest/Universal Input Schema as the OCR/OpenCV upload path — the Design Planning Layer and Prompt Builder don't need to know whether a project's rooms came from an upload or a sketch. This path's data is actually more reliable than the upload path's, since it's constructed directly by the user rather than detected from an image.

**Why Phase 2, not MVP**: even the simplified grid-block version is more engineering than the Q&A form (room list + sqft) already locked in as the MVP no-floor-plan path, and ships no additional pipeline capability the Q&A form doesn't already unlock (same downstream JSON shape, minus explicit openings, which the AI can reasonably assume are unspecified without them). Worth building once real usage shows clients want visual room layout instead of typing a list — not worth building speculatively now.

## Database model
Extends `supabase/schema.sql` with:
- **`profiles`** (built on Supabase Auth's `auth.users`, see Workstream 2) — display_name, `role` (`user` | `master`, simplified from an earlier 3-tier user/admin/master design — no separate admin tier, `master` has full access), `status` (`active` | `trial_ended` | `suspended` | `pending_approval`), `trial_ends_at`, created_at. `master` = Vastos team/owner, `user` = the client (construction/design firm) who logs in and generates visuals.
- **`ai_usage_logs`** — user_id, feature (ocr/semantic/room-image/edit/video), provider, model, success, duration_ms, estimated_cost, created_at. Aggregated in the admin console for the "Gens" and "Lifetime Cost" columns and the 7D/30D/90D/365D spend cards.
- **`approvals`** — for the Approvals tab: new client accounts created but not yet activated (id, requested_by, user_id, status, created_at). MVP: table + tab exist, activation logic is a Phase 2 stub (see CTO review section) since admin-issued credentials mean nothing populates this queue yet.
- **`projects.status`** — the state-machine enum (`created`, `floor_plan_uploaded`, `parsing`, `needs_review`, `ready_for_generation`, `generating_images`, `images_ready`, `editing`, `generating_walkthrough`, `completed`, `failed`). Single source of truth for lifecycle; the frontend reads this instead of maintaining separate boolean flags.
- **`projects.manifest`** — one JSONB column holding the project manifest: metadata, the project's Universal Input (design selections + additional requirements), detected rooms (+ user edits), the cached Design Specification (from the Design Planning Layer), generation settings, and a pointer to each room's *currently selected* generation. Kept as a single column on the existing row rather than a new subsystem.
- **`generations`** — the version-history table: id, project_id, room_key (or null for a video/walkthrough-level generation), type (`image` | `edit` | `video`), storage_url, the version fields also mirrored here (`pipeline_version`, `system_prompt_version`, `planning_prompt_version`, `prompt_builder_version`, `design_spec_version`, `model_used`), created_at. Every "Generate", "Generate more", and Lasso edit call inserts a new row rather than overwriting one — this is what "Final image selection" (step 7a) and any future "view history" UI browse and select from. Kept separate from `ai_usage_logs` on purpose: `generations` holds product-facing output artifacts a user browses/restores, `ai_usage_logs` holds cost/analytics data the admin console aggregates — same underlying events, different consumers, so they stay separate tables rather than overloading one.
- **`prompt_templates`** — versioned, admin-editable, `type` enum (`system` | `planning` | `builder`), `category` (nullable, set for `planning`-type rows to hold the per-project-category planner persona; null for `system`/`builder` which are category-agnostic), version, body (structured JSON), `published` (bool), created_by, created_at. Only the published version of each type is used by the pipeline; drafts are editable without a deploy. Replaces the earlier combinatorial `vertical:roomType:style:luxuryLevel` key — see "AI prompting architecture."
- **`feature_flags`** — key, enabled (bool), updated_at. Minimal on/off toggles, no rollout percentage or targeting.
- **`ai_usage_logs`** additionally records `pipeline_version`, `system_prompt_version`, `planning_prompt_version`, `prompt_builder_version`, `design_spec_version`, `model_used`, `post_processing_version`, and `error_category` (`ValidationError` | `AiProviderError` | `StorageError` | `TimeoutError` | `InternalError`) per generation.
- Existing tables (`projects`, `parse_jobs`, `floor_plans`, etc.) gain a `user_id` foreign key once real auth replaces the current anonymous-browser-id model (`src/lib/project-sync.tsx`).

## Config-driven project types
`/config/project-types/{residential,apartment,commercial,custom}.json` — each defines supported room types, walkthrough/video ordering defaults, and the category's planner persona reference (which `planning`-type `prompt_templates` row to use). Adding a new vertical (e.g. a new Custom category like "Lighthouse") becomes a config file plus one persona string, not new code — the Universal Input Schema and Design Specification schema never change per category. Kept intentionally simple (static JSON checked into the repo, not admin-editable yet) — that editability can move into the admin console later if verticals need to change often; no evidence yet that they will.

## Security
A note on the "hide API calls from the inspect tab" request first, since it needs a precise answer rather than a false promise: **no website can hide from a technical user that a network request happened** — the browser's Network tab will always show a call from the frontend to your own `/api/*` routes; that's true of every web app and isn't fixable. What's real, correct, and already mostly designed in above:
- **The AI provider is never visible.** The frontend only ever calls Vastos' own `/api/*` routes, never Gemini/Veo directly, so no API key, provider identity, or provider endpoint is ever exposed to the browser (already locked via the `src/lib/ai/provider.ts` hard rule).
- **API responses stay minimal (new rule, add now).** No API route should ever return prompt text, the Design Specification, template bodies, or other internal pipeline data to the client — only the final image/video URL and minimal UI state. Someone opening devtools sees that a call was made and to which of *our* endpoints, never what we told Gemini or why.
- **Every `/api/*` route is auth-checked server-side (extends the existing route-guard plan)** — not just page navigation. Seeing an endpoint in devtools is harmless if calling it without a valid session does nothing.
- **Signed/expiring storage URLs (new, add now).** Generated room images and walkthrough videos should not sit in a publicly-readable S3 bucket — serve them via short-lived signed URLs (or a private bucket + an authenticated proxy route), so a project's assets aren't guessable or permanently public just because someone had a link. The Export PDF's walkthrough video link is the one deliberate exception — see below.
- **Lightweight rate limiting on AI-triggering routes (new, add now, distinct from the deferred hard spend limits).** A basic per-user request-rate cap (e.g. N requests/minute) is an abuse/cost-control safeguard, not the same thing as the billing/quota feature already deferred to Phase 2 — worth having even with "log only" spend policy, to stop accidental or malicious rapid-fire generation calls.
- **Session/cookie hardening**: httpOnly, Secure, SameSite=Lax (or Strict) cookies (refines the earlier "long-lived httpOnly cookie" auth bullet), passwords hashed with bcrypt/argon2, never plaintext.
- **CSRF**: state-changing API routes validate same-origin (Origin/Referer check) given the app is cookie-session-based, not token-based.
- **Input validation** at every API boundary — file type/size limits on floor-plan upload, text-length caps on free-text fields (Additional Requirements, "Generate more" notes) — feeds the already-planned `ValidationError` category.
- **Role-based authorization enforced server-side**, not just hidden in the UI — every `/console/*` route and its API routes re-check `role = 'master'` on the server, consistent with the "never trust frontend state" rule already adopted from the user's standards doc.
- **Export video link**: unlike other generated assets, this one is meant to be shared with the builder's client, so it's a stable, unguessable (long random token) URL rather than a short-lived signed one — not publicly listed or enumerable anywhere, but not designed to expire either, since builders will reshare it over time.

## Admin console

Structure mirrors the reference screenshot, restyled dark:
- Top stat cards: Users, Spend (period-selectable 7D/30D/90D/365D), Spend Lifetime, Pending approvals.
- Tabs: Overview, Users, Approvals.
- Users tab: searchable table — name/email, status badge, generation count, lifetime cost, actions (Trial / Suspend / Activate / Extend / Delete), "New User" button (master-issued username/password, per the original requirement that clients never self-register).
- Approvals tab: present in the UI for layout parity with the reference, logic stubbed (Phase 2) — no current flow populates it since accounts are master-issued, not self-requested.
- **Prompt Management tab (new, per CTO review)**: list `prompt_templates` grouped by type (System / Design Planning / Prompt Builder), view/edit the structured body, publish a new version per type. Design Planning rows are further grouped by project category (its planner persona). Only the published version of each feeds live generation, so edits are safe to draft without affecting production.

## Full page-by-page flow (residential, this phase; apartment/commercial/custom reuse the same screens with different prompt configs)
1. **Login** (`/login`) — Vastos logo, tagline, username/password box. Session persists via long-lived httpOnly cookie so the client isn't re-prompted on the same device.
2. **Welcome** (post-login home) — "Hello {client}, welcome to Vastos" (bold, top), carousel background, centered "What are you working on today?" with 4 options: Individual home, Apartment, Commercial office, Custom.
3. **Project type → floor plan step** — "Do you have a floor plan?" Yes → upload box (PNG/JPG; single-page PDF rejected today per the existing pipeline behavior, revisit with the Gemini-only detection path). No → Q&A form (room list + sqft) for MVP; the grid-block Sketch Tool (see "No-floor-plan flow" section) is the Phase 2 upgrade to this path, producing the same structured output plus explicit openings.
4. **Room confirmation/edit** — shows OCR+detection output as an editable room list. Per room, individually: rename/retype (e.g. "kids' playroom" → "master bedroom"), edit size, and a free-text "Additional Requirements" box for that room specifically. List-level operations: delete a room, merge/split (combine two entries, or duplicate one into two with new names). "Add a room" reuses the existing `LassoSelect`/`extractLassoRegion` tool unchanged: the user lassos the missed area directly on the uploaded plan image, and it snaps to the real detected wall lines and pulls any printed OCR dimension text inside the loop, same as it already does today. Geometry redraw for merge/split is not part of MVP; the list is what drives the Universal Input's `layout.rooms`. Project status moves `needs_review → ready_for_generation` on confirm.
5. **Design selection (global, applies to every room)** — the 6 locked style presets as visual cards, a Luxury Level choice (Standard / Premium / Ultra Luxury), and a colour picker. Only these three are global; room-specific notes were already captured per room in step 4. These populate the `design` section of the Universal Input Schema — see "AI prompting architecture."
5a. **Design Planning call (backend, not a user-visible screen)** — immediately after step 5, the Universal Input (global design choices + every room's name/size/notes) is sent to the Design Planning Layer, which returns and caches one Design Specification (with per-room guidance for every detected room) on `projects.manifest`. Every room prompt in step 6 is built from this same cached specification via the Prompt Builder, keeping rooms visually consistent with each other without re-planning per room.
6. **Room image generation** — Runway-style workspace: one generated image per detected room (bedroom, hall, kitchen, bathroom, etc.), each final prompt assembled by the Prompt Builder from System Rules + Project Context + the cached Design Specification's slice for that room + that room's Additional Requirements + Camera/Negative Rules. Two actions per room: **click the image** to open it full view and enter Lasso edit (step 7); **"Generate more"** opens a small text box for what should change in the new variation (e.g. "make it brighter"), then generates another full variation of that room incorporating the note — distinct from Lasso edit, which targets a specific spot rather than rerolling the whole room. Every generation (initial, "Generate more", Lasso edit) inserts a new row in `generations` rather than overwriting the previous one — a small thumbnail strip per room lets the user browse and pick among past generations, not just the latest. Runs synchronously for MVP but through the same provider-call shape used for video, so it can move to a background job later without a rewrite.
7. **Lasso edit (full view)** — reuses the existing `lasso-canvas.tsx` mask-painter unchanged; extends it to support up to 2 numbered regions per image, a prompt box per numbered region, "Generate" applies both edits in one inpainting call via `gemini-image.ts`, saved as a new `generations` row.
7a. **Final image selection (new)** — once the user is ready to build the walkthrough, and a room may have several generated/edited variations (from "Generate more" and Lasso edits, all preserved in `generations`), the user confirms exactly one final image per room, plus an include/exclude toggle per room — not every generated room has to appear in the walkthrough (e.g. skip a bathroom).
8. **Walkthrough video** — after final images and inclusion are confirmed, the app shows a default order for the included rooms (from an LLM ordering call, e.g. living room → bedroom → bedroom → kitchen) as an editable drag-and-drop list; the user can reorder by dragging and then confirms. Each included room becomes one 3-second cinematic zoom-in video clip via Veo, generated through an Inngest background job (progress polling, not a blocking request), stitched back-to-back (hard cut, no crossfade) in the confirmed order via the existing `ffmpeg.ts` into one walkthrough video, saved as a `generations` row (type `video`).
9. **Apartment flow** — identical screens and identical Universal Input Schema, `project.subcategory` set accordingly; the Design Planning Layer's persona (from the project-type config) naturally scales its guidance for apartment-sized spaces.
10. **Commercial/Custom flow** — user names the category (e.g. "Dental Clinic", "Restaurant", "Lighthouse"), same upload/Q&A → confirm → design selection → generate flow, `project.category`/`project.subcategory` set accordingly, Design Planning Layer persona switches (e.g. "think like a healthcare architect prioritising circulation, hygiene and comfort" for a clinic) while the JSON contract and every downstream screen stay identical to residential.
11. **Profile** — **DONE (v1).** `/profile` (`src/app/profile/page.tsx`): account card (display name, email, trial/status pill, sign out) plus a project list/count reusing the same local-first store `/projects` already uses (the real `projects` table isn't wired into any live page yet — see Workstream 3 — so a DB-backed usage query would just read zeros today). Deliberately shows counts only, never dollar cost (that's admin-only, Workstream 9). A proper cross-project "Recent Generations" view and a real generation count wait on the `generations` table (Workstream 11's table build-out) and the Workstream 8 frontend migration onto the real `projects` table.
12. **Export (new)** — available once a project has a completed walkthrough video. Generates a PDF (cover page, client name, project details, the final selected room renders, selected aesthetic, colour palette, and a link to the walkthrough video, not a QR code) — a presentation document a builder can hand directly to their client.
13. **Room-size illusion mitigation** — applied at generation time, not a separate screen: real room dimensions injected into each room's prompt to drive framing, plus a small disclaimer near generated images noting visuals are illustrative and proportions follow the floor plan.
